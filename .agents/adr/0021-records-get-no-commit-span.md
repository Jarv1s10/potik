# Records get no commit span

`TracingMiddleware` gave each handled record a `commit {topic}` span, a child of its `process` span, from the handler's return until its transaction committed, with a link to the transaction's span. It ended with an error if the record never committed. The middleware sees only each record's return and each transaction's next offsets, so it matched them by assuming that a partition's records return in offset order, and that a record returning at or below an earlier one's offset was a replay. Key concurrency (ADR 0020) broke that assumption on its normal path: a record that returned before an earlier one ended its span as "handled again", with no link, and a held record that the core dropped could later be linked to a transaction that never committed it. We removed the span.

Little depends on it. Exactly-once already shows which handling of a record committed: only committed outputs reach downstream consumers, so when a record runs again, only the committed handling's `create` spans have a link from a transaction's span and a downstream `process` span. Transaction failures keep their spans, because a failed transaction is always traced. What we lose is a link from a record without outputs to its transaction, and the time from a handler's return to its commit, which includes the wait behind an earlier record under key concurrency. Lag metrics answer the first for operators, and `RuntimeStatus.oldest_uncommitted_at` covers stuck commits. Removing the span also halves the spans of a record without outputs, and a transaction no longer creates one span per record that it commits.

We rejected matching records to transactions by offset. It works from rules the core guarantees, that a transaction commits every returned record below its next offset, and that a record that does not return blocks every later record of its partition, but it keeps the middleware's correctness tied to the core's commit order, which this bug showed is easy to break unnoticed. We rejected having the core report which records each transaction commits or drops, because it adds public surface and per-record state to the core for one consumer. Either can return if users need per-record commit timing.
