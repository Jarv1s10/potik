# Buffered records are budgeted in bytes

`max_buffered_records` limited the fetched records that wait for their handler by count, and a count is a poor measure of memory: 10,000 records take 1MB at 100B each and 50MB at 5KB each. With consumer lag the buffers stay full, so the budget is the app's steady memory, which its Kubernetes memory request must cover. Operators size that in bytes.

So `max_buffered_bytes` replaces it, at 16MB by default. A record counts as the length of its key and value plus a fixed 350 bytes: about 250 bytes of Python objects, and about 100 bytes of a `traceparent` header in librdkafka's C memory, both measured with 100,000 consumed records. Headers are not measured per record, because confluent-kafka keeps them in C until something asks for them, and asking converts them to Python objects: about 4µs and 580 bytes per record with three typical headers, more than their raw size. A typical record, a UUID string key, 0.5-2KB of JSON, and a `traceparent`, then counts as about 1.4KB, so 16MB holds about 12,000 of them, close to the 10,000 records of the old default. Handlers that do I/O need only a few buffered records each. With 300 partitions, each share holds about 40 typical records, seconds of work at 10-100ms per record. The count is an estimate. The allocator rounds each allocation up, which on macOS added about 730 bytes of RSS to each record of 1KB of JSON. Each share is at least 16KB, one batch of the Java producer's default size, so with more than 1,000 partitions the total exceeds the budget.

A fetch takes about half a share. confluent-kafka's `consume()` counts records, not bytes, so a fetch takes as many records as fit at the mean size of the previous fetch's records. The first fetch of a run takes one record. A fetch of larger records than the previous one exceeds half a share, by at most librdkafka's prefetch queue, which potik's defaults limit to about 24MB.

The budget in bytes also helps handlers that take about a millisecond or less. librdkafka queues the records of all partitions in one queue, a fetched record batch at a time, and confluent-kafka exposes no queue per partition. A partition whose share holds less than one batch pauses in the middle of it, and the pause drops the rest of the batch, which librdkafka fetches again. With 1MB input batches, 32 partitions, and a 1ms handler, the old default fetched every record twice and committed 10k records/s. 16MB commits 14k, and 32MB 20k. Producers rarely fill 1MB batches at the rates of one partition, because `linger.ms` sends them first, so this matters mostly for backlogs written fast. Shares in bytes cannot remove the single queue: with batches larger than `max.partition.fetch.bytes`, each broker response carries one partition (KIP-74).

The cost is deeper buffers for few partitions. The old default capped a share at 1,000 records, and 16MB gives each of 4 partitions 4MB. A handler that does nothing, with 4 partitions of 128-byte records, commits 108k records/s instead of about 125k, and its process peaks at 61MB instead of 51MB. Sizing records costs about 40ns each and is not the cause. Nor are garbage collection or the size of a fetch: the probe shows the poller waiting more often for librdkafka's queue. We accepted it, because potik's own CPU per record bounds only handlers that do no I/O, and those scale with processes. A cap on a share in bytes, or on a fetch, would add a constant that tunes this one case.

We rejected a larger default `max_buffered_records`, which suits one record size only and multiplies the memory of large records. We prototyped a limit per partition in seconds of handler work, with each fetch taking the whole free budget. It stopped the second fetches, but the partitions that got batches first took the whole budget while the others starved, and the 4-partition benchmark fell to 60k records/s. A larger `max.partition.fetch.bytes` lets a response carry more partitions, but each pause then drops more: librdkafka fetched every record 2.25 times at 1MB and 4 times at 2MB. A larger `queued.min.messages`, and a handler time estimate seeded from the first call, changed nothing.
