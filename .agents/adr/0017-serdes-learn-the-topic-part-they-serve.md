# Serdes learn the topic part they serve

A serde's `decoder()`, `resolver()`, and `encoder()` took only a type. A schema registry serde needs the topic too: Confluent's default `TopicNameStrategy` names a value's subject `{topic}-value` and a key's `{topic}-key`, so the serde could not find a schema from the type alone. Each method now also takes a `SerdeContext` of the topic's name and the part, `"key"` or `"value"`. A `Topic` passes it when it is declared. Serdes that do not depend on the topic ignore it. It is a class rather than keyword arguments, so that a later field breaks no serde.

An encoder stays synchronous, because a topic call encodes right away, so that an `EncodeError` points at the line that made the record. Its I/O, e.g. registering its writer schema, happens before the run. The serde learns every topic part when it is declared, usually at import, so a method of its own, which the service's `main` awaits, can register their schemas. This keeps ADR 0009's rule that potik gives serdes no lifespan. A topic declared during the run must have its schema registered by then too.

We rejected passing only the topic's name, which cannot tell a key's subject from a value's. We rejected a serde lifespan that potik enters, because the serde's client belongs to whoever creates it, as a Producer does (ADR 0001), and `main` already orders its resources with `async with`. We rejected deferring encoding to the commit, where it could await, because an `EncodeError` would then come from no handler and no exception rule could handle it as the record's failure.
