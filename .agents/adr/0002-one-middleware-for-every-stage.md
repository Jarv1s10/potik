# One middleware class for every stage

A middleware class may have all four stages: a `lifespan`, a record (`handle`), a transaction (`commit`), and a Send (`send`), so one class, e.g. `TracingMiddleware`, instruments a service whole. An App calls the first three stages, and a Producer `lifespan` around the time it is open, and `send`. The lifespan is an async context manager rather than a `call_next` stage: a Producer opens and closes in two calls, so it has no single call to wrap, and only a context manager lets the owner shield the exit from cancellation without shielding the run. The lifespan takes a `RunScope` or a `ProducerScope` that describes what it surrounds, e.g. a run's config and live status, so middleware such as the topic check, tracing, or metrics takes no arguments that repeat the run's. We rejected a separate base class for Producer middleware, though some of a class's stages then go unused by some services, because instrumentation would otherwise split into classes that each user would have to combine and configure alike.
