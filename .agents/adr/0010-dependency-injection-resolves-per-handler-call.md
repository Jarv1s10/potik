# Dependency injection resolves per handler call, and the run scope is plain Python

potik's planned dependency injection resolves a handler's `Depends(fn)` parameters once per call. It caches each dependency within the call, and runs the teardown of `yield` dependencies after it. A dependency's parameters use the same markers as a handler's. So one compiler, built once per handler, resolves record parts, the run's context, and other dependencies. Run-scoped resources are not providers. The service creates them in its own code with `async with` before it builds the runtime, and passes them as the run's context, the only bridge into injection. Middleware stays outside injection, because the core and `potik.middleware` must work without the typed layer. It takes run resources in `__init__`, and hands per-record values to dependencies through `ContextVar`s, since a record's middleware and handler run in one task.

We rejected a container with run and record scopes, e.g. Dishka's. It would manage the run's resources and their order, and would need a registry of overrides for tests, beside the `async with` that a service already writes. We rejected FastAPI's split of lifespan state and `Depends`, which needs glue code between the two. A `yield` dependency's teardown runs before the Kafka transaction commits, so injection does not make a database write exactly-once.
