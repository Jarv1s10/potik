# Dependency injection resolves per handler call, and the run scope is plain Python

potik's dependency injection resolves a handler's `Depends(fn)` parameters once per call. It caches each dependency within the call, and runs the teardown of `yield` dependencies after it. A dependency's parameters use the same markers as a handler's. So one compiler, built once per handler, resolves record parts, the run's context, and other dependencies. A call decodes each part of the record once, for every parameter that takes it alike, because a decode can cost more than a whole record's other work. Run-scoped resources are not providers. The service creates them in its own code with `async with` before it builds the runtime, and passes them as the run's context, the only bridge into injection. Middleware stays outside injection, because the core and `potik.middleware` must work without the typed layer. It takes run resources in `__init__`, and hands per-record values to dependencies through `ContextVar`s, since a record's middleware and handler run in one task.

Dependencies resolve one at a time, in the call's task, in parameter order. Sync dependencies run on the event loop, like the rest of the call, because a thread cannot be cancelled. A teardown sees the call's exception but cannot suppress it, since a suppressed exception would commit the record without the exception rules. The exception is a cancellation that the dependency's own cancel scope caught, e.g. `anyio.move_on_after()` around `yield`, which ends the call without outputs: raising it again would stall the partition. A dependency that swallows an outer cancellation, e.g. a revocation's, suppresses nothing, so the record does not commit. A teardown that raises fails the call. potik does not shield teardowns from a cancelled call. A dependency shields its own awaits, with a timeout of its own, because potik cannot pick one that fits every dependency within `rebalance_timeout_ms`. A `yield` dependency's teardown runs before the Kafka transaction commits, so injection does not make a database write exactly-once. Tests have no registry of overrides: they call handlers directly, or pass fakes as the run's context.

We rejected a container with run and record scopes, e.g. Dishka's. It would manage the run's resources and their order, and would need a registry of overrides for tests, beside the `async with` that a service already writes. We rejected FastAPI's split of lifespan state and `Depends`, which needs glue code between the two. We rejected FastDepends, the library closest to this design. It runs sync dependencies and sync `yield` dependencies on threads, it took about 28µs per call where potik's resolver takes about 2µs, and potik would still parse every signature itself to check it against the topic.

We rejected resolving independent dependencies concurrently, as Litestar does for each level of the graph and `di` does as an option. A task group costs about 50µs, more than a whole record's handling at full throughput, and a signature does not tell potik which dependencies do I/O. A `yield` dependency started in a child task and resumed in the call's task cannot hold a cancel scope across `yield` or reset a `ContextVar` token. Two concurrent failures raise a group, which exception rules then see as a group (ADR 0015). Fetching several things at once fits in one dependency that runs its own task group. An opt-in for plain `async def` dependencies could come later without breaking this order, while making concurrency the default could not be undone.
