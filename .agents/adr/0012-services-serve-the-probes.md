# Services serve the probes from their own HTTP framework

potik serves no HTTP. `Runtime.liveness()` and `Runtime.readiness()` return why a probe fails, or `None`, and a service serves them from its own HTTP framework, next to checks of its own, e.g. a database ping. The server runs as a task next to `runtime.run()` in the service's `main`, so the runtime keeps its signal handling, and a failed run stops the server and exits the process for the platform to restart it.

We rejected a `HealthMiddleware` that served the probes from the run's lifespan on a stdlib HTTP server. It cost about 1 MiB of RSS against about 8 MiB for Starlette and uvicorn, and neither changed throughput, but it made potik maintain an HTTP server with its own timeouts, error handling, and OpenTelemetry instrumentation. Its stdlib imports also cost every process about 2.4 MiB, probes or not. A framework's own instrumentation gives the probes the same HTTP semantic conventions, and its routes reach the service's resources through the framework's own injection. We also rejected running the runtime in the ASGI app's lifespan: there, the server owns the signals, and a failed run leaves the server up until a liveness probe fails.
