# Test apps on librdkafka's mock cluster, under the real Runtime

To test a whole app without Kafka, `potik.testing.MockCluster` runs librdkafka's mock cluster in the test process. The app's own clients connect to it, so its `Runtime`, middleware, lifespan, topic check, and transactions run as in production, and a test points the app's `Config` at the cluster. confluent-kafka doesn't wrap the mock cluster, so `MockCluster` calls its C API through `ctypes`, on the librdkafka that confluent-kafka bundles. We rejected faststream's approach, which delivers published records straight to the handlers, because most of potik's correctness lives in the Runtime: partition workers, transactions, failure stopping, retries, and lifespans. A broker that bypassed it would test everything except what fails in production. For the same reason, we removed `App.handle`, which ran one record through the handler and the `handle` stage of the middleware, and put a test entry into the production API.

We first planned an in-memory broker of our own, with fake confluent-kafka clients that `potik.core.clients` would hand out. We dropped it, and `potik.core.clients` with it, because the mock cluster runs the real clients and the real protocol, so its behavior can't drift from librdkafka's the way a fake's would. Neither Python mock library could run the Runtime: mockafka-py stubs out transactions and rebalance callbacks, and kafka-mocha times out `consume()` with `SIGALRM`, which works only on the main thread. The price is the mock cluster's gaps. It doesn't store the offsets that a transaction commits, or fence stale members, so tests on it check outputs, never commits or restarts. The runtime's guarantees are tested against a real broker anyway. We also rejected a public connection object that `Config`, `Producer`, and the middleware scopes would share, with an in-memory one for tests. Every app would then have to pass it through to wherever it builds its `Config` and `Producer`.
