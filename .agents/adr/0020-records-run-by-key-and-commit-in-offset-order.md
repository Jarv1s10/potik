# Records run by key, and commit in offset order

A partition handled one record at a time, so an instance ran at most one handler call per assigned partition. Handlers that wait on I/O, e.g. an HTTP API, then left the instance idle unless the topic had many partitions, and partitions are costly to add. Most topics need order only per key, so a topic may now run by key: `Runtime(key_concurrency={"orders": 64})`, or `@router.handler(orders, key_concurrency=64)`. Records with the same key run one at a time, in offset order, and records with other keys run concurrently. All null keys count as one key, because a producer may rely on null keys and one partition for a total order.

A record that finishes before an earlier record of its partition waits, with its outputs, until every earlier one has finished. The committer then gets the records in offset order. A transaction commits a partition's next offset, so outputs that committed past an unfinished record would be produced again when it replays. Holding them keeps the committer, `Transaction`, offset policies, and rebalances as they were, and exactly-once outputs need no new argument.

A record counts toward its partition's share of `max_buffered_bytes` from its fetch until it goes to the committer, also while it runs or waits. The budget then bounds all of a partition's records, and memory per instance stays independent of the number of assigned partitions (ADR 0019). A slow record lets the records behind it run until they fill the share, and then the partition pauses, so a slow record blocks at most a share of work. A topic's limit counts the keys whose records run, across its partitions in the instance, not per partition, so that it also stays fixed through rebalances and maps to the resources of the pod. A key's record runs during its retries' backoff too, so a `ConcurrencyMiddleware` still limits the handler calls, e.g. to a database pool's size.

A key's task keeps its slot while the key has records. Under lag, a partition with few keys, e.g. a keyless one, would then hold its slots and starve the topic's other partitions whenever the limit is below the number of assigned partitions. So while other keys wait for a slot, a key gives up its slot after each record and queues again behind them, in the semaphore's FIFO order. This costs a semaphore round trip per record, and only while slots are contended.

A handler failure stops the partition at the lowest failed record. The records above it are cancelled, because they could never commit, and those below it, running or waiting for their key, still run. So every record before the failed one commits, as before, and a restart starts at it. The partition is stopped and paused at once, not when the records below it finish, so alerts on stopped partitions (ADR 0013) do not wait for them. A failure that fails the run (`stop_failed_partitions=False`) cancels every record at once instead, as the sequential path fails at once.

We rejected committing out-of-order records at once with a map of the finished offsets in the commit's metadata, as Confluent's Parallel Consumer does, which then skips them on replay. It replays less and lets a slow record hold back no outputs, but it needs an encoding, a fallback when the map exceeds the broker's 4KB `offset.metadata.max.bytes`, which blocks like a full share anyway, and skip logic on every assignment. Tools that read committed offsets would also count finished records as lag. The Parallel Consumer's transactional mode also locks out produces while it commits, which potik's commits need not do. It remains possible on top of this design if replays grow costly.

We rejected hashing keys into a fixed number of lanes per partition, like Karafka's virtual partitions. It needs no map of the keys in progress, but two keys that share a lane block each other, which users cannot see or tune. We rejected a limit per partition, which changes the instance's concurrency and memory with each rebalance, and a count of held records separate from the byte budget, which would add a setting that tunes the same memory.
