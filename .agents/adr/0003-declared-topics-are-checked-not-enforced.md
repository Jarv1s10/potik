# Declared topics are checked at startup by a middleware, not enforced

Potik creates no topics by default, so a record to a missing topic fails only when it is produced: after its handler has run, and maybe after expensive or side-effecting work. So `TopicCheckMiddleware` checks in its lifespan that topics exist before a run handles or a Producer sends anything. It checks exactly the topics it is given. The App gives it the handled topics and every declared output topic. Topics are declared next to the code that produces to them: on a handler or a Router, and in a middleware's `output_topics`, e.g. for dead letters, so a handler shared through a library brings its topics into every service that uses it. Declarations belong to the typed layer: the core Runtime and Producer have none, and a core service passes its topics to the middleware itself. The check is a middleware rather than part of the runtime, like the concurrency limits: an App adds it by default, and a core Runtime or a Producer has it only if its middleware includes it. We accept that core users opt in, as Starlette users do for what FastAPI adds, because the core then holds no policy, a service can replace the check, e.g. with one that creates missing topics in development, and the check fails before other lifespans open resources. It costs one extra client connection at startup. We rejected a single list of topics to check, which drifts from the code that produces. We also rejected failing Outputs or Sends to undeclared topics: it would burden services that rely on existing or auto-created topics, which need no declarations.
