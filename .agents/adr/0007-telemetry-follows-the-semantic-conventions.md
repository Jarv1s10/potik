# Telemetry emits only the semantic conventions, and users enrich the current span

`TracingMiddleware` and `MetricsMiddleware` emit only what the OpenTelemetry semantic conventions for Kafka define, so a user never has to reimplement them to remove potik's own choices. They always set every Required attribute, and every Conditionally Required one whose condition holds, because backends and dashboards rely on them. An `attributes` argument picks the Recommended and Opt-In attributes, as the conventions let an instrumentation do. The key stays off by default, although the conventions recommend it, because keys often identify people. Attribute names come from `opentelemetry-semantic-conventions`, a dependency of the `otel` extra, although its messaging names live in `_incubating` while the conventions are in Development, and each release pins an exact `opentelemetry-api` version. We accepted that, as the OpenTelemetry contrib instrumentations do, so that a renamed convention breaks a test instead of drifting silently.

We rejected hooks per span kind, such as contrib's `consume_hook` and `produce_hook`. Inside `TracingMiddleware`, the current span is already the `process` span in `handle`, the transaction's span in `commit`, and the `send` span in `send`. So a handler, or a middleware after the tracing one, can add attributes and rename spans through `trace.get_current_span()`, and a handler sees decoded values, where a hook would see only bytes. Hooks would add five arguments for the same capability. Only the `create` spans stay out of reach, and a hook for them can be added later without breaking anything. Metrics take no hooks, because an SDK `View` already renames metrics, drops attributes, and changes buckets.

`TracingMiddleware` samples transactions itself, with `transaction_sample_ratio`, instead of shipping a `Sampler`. A sampler decides when a span starts, so it cannot trace every failed transaction, and its base class is in the SDK, which the `otel` extra leaves out. The middleware knows the outcome: it starts the picked share of spans up front, and starts the span of any other transaction that fails once it has failed, backdated to the transaction's start. Record traces stay with the tracer provider's sampler, and outcome-based sampling of whole traces with the Collector's tail sampling.
